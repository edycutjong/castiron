# `Manifest.verify()` does not re-hash the asset payload — a re-encoded file still verifies

**Component:** `genblaze-core` · `Manifest.verify()` / media handler `verify()`
**Type:** verification-integrity gap + docs clarity
**Severity:** medium (provenance is a primary selling point; the gap is easy to misread as "content is tamper-proof")
**Env:** `genblaze==0.4.1` (genblaze-core 0.3.4), Python 3.11, macOS; `mutagen` installed so MP3 embedding is inline. Repro base dumped by `scripts/sdk_introspect.py`.

## Summary

`Manifest.verify()` validates the **canonical hash over the run record** and requires each
output asset to declare a 64-hex `sha256`. It does **not** fetch `asset.url` / re-read the
embedded media bytes and recompute their hash. So editing the embedded manifest is caught
(good), but **re-encoding or splicing the actual audio/image payload is not** — the file still
`verify()`s as authentic as long as the manifest block is internally consistent.

## Minimal repro

```python
from genblaze_core.media import get_handler, guess_mime

# episode.mp3 has an inline ID3 manifest produced by SmartEmbedder.
handler = get_handler(guess_mime("episode.mp3"))
assert handler.verify("episode.mp3") is True          # authentic — as generated

# Re-encode / alter the AUDIO frames only, leaving the ID3 manifest block intact:
#   ffmpeg -i episode.mp3 -af "atempo=1.03" tampered.mp3   # different audio bytes
#   (then copy the original ID3 TXXX:genblaze:manifest frame across unchanged)
assert handler.verify("tampered.mp3") is True          # STILL True — payload not re-hashed
```

The manifest records `asset.sha256` of the originally generated bytes, but `verify()` never
recomputes the *current* file's stream hash to compare against it.

## Observed vs expected

- **Observed:** `verify()` == `verify_hash()` (canonical hash of the run record) + a presence
  check that every output has a `sha256`. The docstring is honest about this ("does not fetch
  `asset.url` or re-hash remote bytes"), but the top-line docs ("verify that an asset has not
  changed") read as full-content integrity.
- **Expected (opt-in):** a mode that recomputes the media payload hash and compares it to the
  manifest's recorded `asset.sha256`, so a re-encoded/spliced file fails verification.

## Impact

Our tamper red-path demo catches manifest/provenance edits today. To catch an audio re-encode
(the more intuitive "tamper" a judge will try), we add a CastIron-side `verify_episode()` that
re-hashes the decoded/embedded stream vs `manifest.assets[i].sha256`. That belongs upstream —
every consumer who trusts "verify" for content authenticity needs it, and most won't realize
the payload isn't covered.

## Proposed API

```python
# opt-in payload re-hash (default False preserves today's cheap, offline check):
manifest.verify(re_hash=True)                 # recompute embedded/asset bytes vs recorded sha256
handler.verify("episode.mp3", re_hash=True)   # same at the media-handler layer
```

At minimum: tighten the one-line docs to say `verify()` covers the **provenance record**, not
the media payload, and point to the re-hash path once it exists.

## Related

Pairs with the "no `genblaze` CLI" gap (separate issue): `genblaze verify FILE` is documented
but unshipped, so today both the app check and the CLI-parity check route through
`get_handler(mime).verify()` — a `re_hash` flag would flow to both.
